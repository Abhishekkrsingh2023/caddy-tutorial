# 04 — Reverse Proxy to a FastAPI App

**Goal:** Use Caddy as a reverse proxy in front of a Python FastAPI application running on port 8000.

---

## Theory

A **reverse proxy** receives requests from the public internet and forwards them to a backend application running privately on the same machine (or another server). The backend never talks to the internet directly.

Why not expose FastAPI directly?

- FastAPI's built-in server (`uvicorn`) is not designed to handle raw internet traffic at scale.
- It has no TLS, no request rate-limiting, and no access logging by default.
- Caddy adds all of that in front, transparently.

The `reverse_proxy` directive in Caddy takes a backend **address** (host:port) and forwards every matching request to it. Caddy also sets the standard `X-Forwarded-For` and `X-Real-IP` headers so your app can see the original client's IP address.

---

## Code

**`examples/04-reverse-proxy/app.py`**

```python
# Install dependencies: pip install fastapi uvicorn
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def root():
    return {"message": "Hello from FastAPI!"}

@app.get("/health")
def health():
    return {"status": "ok"}
```

**`examples/04-reverse-proxy/Caddyfile`**

```caddyfile
localhost {
    reverse_proxy localhost:8000
}
```

---

## Line-by-line Explanation

```
localhost {
```
Opens a **site block** for `localhost`. Caddy will listen on this address. The curly brace opens because we have one directive inside.

```
    reverse_proxy localhost:8000
```
The `reverse_proxy` directive takes the backend address as its argument. Every request that arrives at `https://localhost` is forwarded to `http://localhost:8000`. Caddy handles the TLS on the public side; the connection to `localhost:8000` is plain HTTP (since it's on the same machine — no need to encrypt local traffic).

```
}
```
Closes the site block.

## Run It

**Terminal 1 — start FastAPI:**

```bash
cd examples/04-reverse-proxy
pip install fastapi uvicorn
uvicorn app:app --host 127.0.0.1 --port 8000
```

**Expected output:**

```
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
```

**Terminal 2 — validate and start Caddy:**

```bash
cd examples/04-reverse-proxy
caddy validate --config Caddyfile
caddy run --config Caddyfile
```

**Expected output from validate:**

```
Valid configuration
```

## How Caddy Passes the Request

```
curl ──► Caddy :443 (TLS) ──► localhost:8000 (plain HTTP)
                │
                ├── Adds X-Forwarded-For: <client-ip>
                ├── Adds X-Forwarded-Proto: https
                └── Adds X-Real-IP: <client-ip>
```

Your FastAPI app can read these headers to know the real client IP, even though it only sees requests from `127.0.0.1`.

---

## Common Mistakes

1. **FastAPI not running when Caddy starts** — Caddy will start fine even if the backend is down. Requests will return a `502 Bad Gateway` error until the backend is up. Always start the backend first.
2. **Using `0.0.0.0` vs `127.0.0.1` for the backend** — Binding FastAPI to `127.0.0.1` (loopback) means only the local machine can reach it, which is what you want. Binding to `0.0.0.0` exposes it on all network interfaces and bypasses Caddy's protections.
3. **Backend URL in Caddyfile has no `http://` prefix** — `reverse_proxy localhost:8000` is correct. Writing `reverse_proxy http://localhost:8000` also works, but is not required for plain HTTP backends.
